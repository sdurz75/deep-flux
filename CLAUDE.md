Guida al repository: le scelte sono vincoli deliberati per tenere il progetto snello. Struttura, classi e package si ricavano dal repo (`git ls-files`) e dai test di architettura; qui solo cio' che non e' ovvio. ## Estensioni hexa-* e UI del core

La dipendenza Maven va dall'estensione (`hexa-pwa`, `hexa-ai`, `hexa-oauth2`) al core, mai il contrario: una libreria opzionale che ha UI ingaggia il core **implementando una porta del core**, che il core raccoglie come `ObjectProvider`/`List` (vuota senza estensioni). Mai due `<template>` con lo stesso path in due jar (vince uno a caso), mai il core che nomina l'estensione. Le porte: `core.web.ILayoutContributor` (fragment per `<head>`, fine `<body>` e toolbar dopo la campanella — `hexa-oauth2` vi mette l'avatar dell'utente, foto dal claim OIDC `picture` —, voci del menu «Gestione»; aggregate da `LayoutSlotsAdvice` nei model attribute `headFragments`, `bodyEndFragments`, `toolbarFragments`, `manageMenuEntries`, inseriti dal layout con `th:each` + `th:insert` ANNIDATI: sullo stesso elemento `th:insert` ha precedenza e la variabile non esiste ancora; il nome si preelabora con `~{__${...}__}`) e `core.lock.port.in.ILockExemptPaths` (path che il blocco con PIN lascia passare). I fragment contribuiti non hanno parametri: i dati arrivano dal model (`@ControllerAdvice` dell'estensione). Si prova con un host di prova fuori da `org.dual.hexa`.

## Configurazione dei moduli (`core.config`)

Il modo PRINCIPALE di configurare i moduli hexa-* che ne hanno bisogno: niente `@Value` per valori che l'utente deve poter cambiare. Il modulo implementa la SPI `core.config.port.in.IConfigModule` (un bean: si autoregistra; id slug unico, `titleKey`, `fields()` di `ConfigField` TEXT|INT|BOOL|COLOR|SELECT|SECRET|LIST|COLLECTION, `validate(ConfigChange)` per i controlli fra campi, `fragment()` facoltativo SENZA parametri con i dati dal model via `@ControllerAdvice` del modulo). Il core genera `/settings` (`SettingsController`, una SCHEDA per modulo con `fragments/core/tabs`: `?module=<id>`, il primo se manca o e' sconosciuto, e si rende solo la sezione attiva; schede = link normali; i campi si raggruppano in riquadri con titolo (`IConfigModule#groups()`, `ConfigGroup`; non elencati = riquadro finale senza titolo) disposti in una griglia che si allarga su schermi grandi, con gli elenchi di record a tutta riga; le modifiche non salvate si perdono cambiando scheda; stessa URL due risposte da `HX-Request`) e la voce «Impostazioni» del menu «Gestione» (`SettingsLayoutContributor`, vuota senza moduli). I valori si leggono a ogni uso da `IModuleSettings#values(id)` (mai in un campo: vale senza riavvio): override in DB (`module_config`, nessuna FK) → property `app.<id>.<key>` → `envVar` del campo (alias d'ambiente, es. `HX_OAUTH2_ENABLED`) → default del campo. `save` e' tutto-o-niente; `ConfigException` e' `REJECTED` (messaggio nella sezione, niente registro). `SECRET` = segreto `ISecrets` di `secretType` (tipo `managed` registrato dal modulo), nome `<modulo>/<chiave>` o `<modulo>/<chiave>/<idRiga>/<colonna>` (max 60: controllato all'avvio, `idColumn` max 20), MAI in `module_config` ne' nell'HTML (solo le ultime 4 cifre; vuoto = lascia com'e'; senza chiave di cifratura il salvataggio e' rifiutato). `LIST` = voci a-capo-separate in `module_config` (`additive`: property/env si SOMMANO alle salvate; `lowercase`, `validation`); `COLLECTION` = array JSON SENZA segreti, form `<chiave>.<id>.<colonna>`, riga nuova `<chiave>.__new.<colonna>`, rimozione `<chiave>.<id>.__remove`, mai annidata. Il reset cancella anche i segreti del modulo. I testi del modulo stanno nel SUO bundle; `settings.*` nel core. Nel template della sezione l'`<input>` ha `id="cfg-input"` statico solo perche' `clear-field :: wrap` lo seleziona (a runtime vale `th:id`). `app.pwa.enabled` resta decisione di avvio (alias d'ambiente `HX_PWA_ENABLED`, default true, letto da `PwaEnabledCondition`). **UI imposta dal core** (template `settings-section.html` + componente Alpine `settingsForm`): form e bottoni per modulo, «Salva» disabilitato finche' il FormData non differisce dallo snapshot salvato (`primaryDirty`/`neutralDirty` in `button.html`), «Annulla modifiche» = `GET /settings/{modulo}` (rilegge lo stato salvato, niente `form.reset()`), «Predefiniti» = `POST .../reset` con conferma, toast di successo via `HX-Trigger system-toast` con chiave unica a ogni esito; dopo un rifiuto la sezione ha `data-initial-dirty="true"`. Un `fragment()` di modulo sta DENTRO il form (mai suoi `<form>` o bottoni di salvataggio) e ne eredita il tracciamento. Primo consumatore: `PwaConfigModule`/`PwaSettings`.

## Blocco con PIN (`core.lock`, nel core: non e' una feature PWA)

Single-user: un PIN (4-8 cifre) blocca l'app dopo un periodo di inattivita'; senza PIN il blocco e' spento e non cambia nulla (opt-in dalla pagina `/security`, voce del menu «Gestione»). **Il cancello e' lato server** (`LockInterceptor` su `/**`): a sessione bloccata passa SOLO `/unlock`, `/lock/now`, `/js/`, `/css/`, i path di `ILockExemptPaths` e `app.lock.exempt-paths`; `/images/**` ed `/events` compresi (401). Navigazione = redirect a `/unlock?next=` (solo path locali, mai `//host`), htmx = 401 + `HX-Redirect` (tranne se gia' su `/unlock`: ciclo), il resto 401 secco. Lo stato e' nella SESSIONE HTTP (un altro browser parte bloccato; `changeSessionId` allo sblocco): ultimo input dell'utente aggiornato SOLO da sblocco e `POST /lock/touch`, che il client (`fragments/core/lock-idle.html`) invia per input VERI: il polling (aggiornamenti periodici, crediti, SSE) non deve contare, o l'app non si bloccherebbe mai. Scaduto timeout + 30 s il server blocca da solo. PIN = hash PBKDF2-HMAC-SHA256 (600.000 iterazioni, sale casuale, confronto a tempo costante) in `app_lock` (una riga, mai il PIN); dal 4o errore i tentativi rallentano (5 s raddoppiando fino a 15 min, persistito). Ogni modifica a un blocco attivo chiede il PIN attuale; `LockException` e' `REJECTED` (messaggio nel form, niente registro). Recupero di un PIN dimenticato: `app.lock.reset=true` (o la variabile `HX_LOCK_RESET=true`) all'avvio lo spegne senza PIN e lo scrive negli eventi; togliere la proprieta' dopo l'uso. Alternativa che tiene il blocco acceso: `java -jar app.jar set-pin <pin>` (`LockCliRunner`, profilo `backup` = niente web, imposta il PIN SENZA chiedere quello attuale e ESCE con 0/1/2; `ILock#forceSetPin`: spento = lo attiva col timeout di default, acceso = cambia PIN tenendo il timeout e azzerando i tentativi). Modello di minaccia: dispositivo incustodito o altro browser, non cifra nulla (i prompt in `localStorage` restano in chiaro). Senza `hexa-oauth2` il PIN e' l'unico accesso (nessuno Spring Security); con `hexa-oauth2` il PIN resta sopra l'accesso OAuth2. Non verificato dal vero: lo script di inattivita' nel browser e il redirect dentro il service worker della PWA.

## Accesso con OAuth2 (`hexa-oauth2`)

Cancello di primo livello opzionale: autentica con un provider OIDC (Google, Microsoft con tenant, Keycloak...) e lascia entrare SOLO chi e' in una lista (email esatte e domini). Spring Security c'e' SOLO con questo modulo, e la sua `SecurityFilterChain` (`OAuthSecurityConfig`) e' l'unica: non aggiungerne altre.
- **Spento = invisibile.** Default spento; la catena e' statica e l'interruttore e' un dato (`IOAuthAccess#isEnabled`, in memoria, letto a ogni richiesta). A cancello spento intestazioni di default e CSRF di Spring Security sono DISABILITATI e nessuna richiesta cambia (`Oauth2GateOffTest`). A cancello acceso il CSRF e' `SameOriginFilter` (`Sec-Fetch-Site`, altrimenti `Origin` contro `Host`/`X-Forwarded-Host`), mai il token: romperebbe ogni POST htmx, i `fetch` keepalive, `/lock/touch` e l'upload della maschera.
- **Durata della sessione.** `SessionLifetimeFilter` (a cancello acceso, utenti autenticati): `session-days` (inattivita' scorrevole, default 30), `session-max-days` (tetto dal primo accesso, 0 = nessuno), `session-remember` (cookie `JSESSIONID` con Max-Age, ri-emesso al piu' ogni ora); campi di `Oauth2ConfigModule`, letti a ogni richiesta, env `HX_OAUTH2_SESSION_*`. I token del provider non si usano dopo l'accesso. Sessioni persistenti su `data/sessions` (`core.yml`): gli attributi di sessione devono restare `Serializable`. Non verificato dal vero: PWA installata, dietro proxy.
- **Fallisce CHIUSO.** Acceso senza provider o senza ammessi nessuno entra. Per questo da UI accendere richiede un provider, un ammesso E un accesso di prova riuscito (riga di `oauth2_login`, scritta da `authorize` quando un ammesso entra e svuotata quando cambiano i provider); con il cancello acceso non si toglie l'ultimo provider ne' l'ultima voce utile. Le precondizioni stanno in `IOAuthAccess#checkChange`, chiamata da `Oauth2ConfigModule#validate` (salvataggio tutto-o-niente). Recupero: `HX_OAUTH2_RESET=true` all'avvio (`OAuthStartupRunner`) spegne il cancello e lo scrive negli eventi; togliere dopo l'uso. `HX_OAUTH2_ENABLED=true` e' AUTOREVOLE: accende senza le precondizioni (responsabilita' del deployer), la UI non lo spegne e, se incompleto, scrive un avviso.
- **Configurazione essenziale = variabili `HX_OAUTH2_*`** (`EnvOAuthSettings`, placeholder annidati, nessun yml da importare; le property `app.oauth2.*` prevalgono): `ENABLED`, `RESET`, `PROVIDER` (`google` = issuer implicito, vuoto = OIDC generico), `ISSUER_URI`, `CLIENT_ID`, `CLIENT_SECRET`, `TITLE`, `ALLOWED_EMAILS`, `ALLOWED_DOMAINS`. Il provider d'ambiente (slug `google` o `sso`) e' VIRTUALE e in sola lettura: il segreto non si salva, non si logga, non sta nel Model (`EnvProvider#toString` non lo stampa). Il resto (interruttore, altri provider come righe `COLLECTION`, elenchi `LIST` additivi con `HX_OAUTH2_ALLOWED_*`) e' il modulo di configurazione `Oauth2ConfigModule` (sezione in `/settings`); il fragment `oauth2-settings :: extra` mostra stato, checklist, indirizzo di ritorno, «Prova accesso» ed «Esci» (dati lazy dal model via `OAuthSettingsAdvice`: un `@ModelAttribute` eager girerebbe prima del salvataggio). Cambiare i provider azzera gli accessi di prova e i legami issuer+subject; un backup ripristinato con un'altra chiave di cifratura non apre il segreto del client: recupero `HX_OAUTH2_RESET=true`.
- **Segreti.** Il segreto del client di un provider da UI e' un segreto di tipo `OAUTH2_CLIENT` di `/secrets` (campo `SECRET` di una riga `providers`, nome `oauth2/providers/<slug>/client-secret`, tipo `managed` registrato da `OAuthSecretTypes`; `IOAuthProviders#clientSecret` lo restituisce a `DynamicClientRegistrations`); `SecretService` aggrega TUTTI i bean `ISecretTypeCatalog`. Mai il segreto in log, eventi, toast o Model.
- **Lista.** Applicata DENTRO l'autenticazione (`AllowlistOidcUserService`, lancia `OAuth2AuthenticationException` prima che il contesto sia salvato), solo con l'id token (nessuna chiamata a userinfo). Logica pura in `AllowPolicy`/`OAuthAccessService` (application, senza tipi Spring Security): email trim+minuscolo e `email_verified` obbligatorio; dominio = UGUALE alla parte dopo l'ULTIMA chiocciola (mai `endsWith`); per le email salvate al primo accesso si legano `issuer`+`subject` (un'altra identita' con la stessa email e' respinta). Un rifiuto scrive un avviso (`loginDenied`) senza rivelare all'utente il motivo.
- **Provider dinamici.** `DynamicClientRegistrations` e' il `ClientRegistrationRepository` (impostazioni + ambiente): discovery `<issuer>/.well-known/openid-configuration` con il `RestClient.Builder` iniettato (`RestRemoteClient`, `remote.call`), controllo che l'`issuer` dichiarato coincida, cache 10 min svuotata da `ModuleConfigChangedEvent`; un guasto si registra (`OAuthEventSource.OAUTH2`) e il provider risulta assente. PKCE sempre. L'avvio passa da `/oauth2/start/{slug}` (verifica prima la registrazione, poi il flusso di Spring); l'indirizzo di ritorno `{baseUrl}/login/oauth2/code/{slug}` e' mostrato per provider (dietro proxy serve `server.forward-headers-strategy=framework`).
- **Percorsi.** Esenti: `/js/**`, `/css/**`, `/error`, `/favicon.ico`, `/oauth2/login`, `/oauth2/start/*`, `/oauth2/authorization/*`, `/login/oauth2/code/*` e TUTTI i path dei bean `ILockExemptPaths` (manifest, `/sw.js`, `/offline`, `/pwa/`: il browser li chiede senza cookie). `/unlock` NON e' esente: prima OAuth2, poi il PIN. `OAuthEntryPoint` ripete le regole del PIN (navigazione = redirect, htmx = 401 + `HX-Redirect` tranne sulla pagina di accesso, il resto 401); la `RequestCache` salva solo navigazioni GET (mai un fetch o un flusso SSE).
- **Test.** Il flusso intero si prova contro un provider OIDC FINTO in-process (`FakeOidcProvider`: discovery, JWKS, token con RSA generata) in un host fuori da `org.dual.hexa` (`com.example.oauth2host`); mai un provider vero. Non verificato dal vero: login con Google/Microsoft, redirect URI dietro reverse proxy a sottopercorso, comportamento dentro la PWA installata.

## PWA (`hexa-pwa`)

Installabile con shell offline, **niente di piu'**. Il worker (`hexa-pwa/src/main/resources/pwa/sw.js`, servito da `PwaController` alla radice del context path: scope giusto senza `Service-Worker-Allowed`, sempre `no-cache`) mette in cache SOLO `/offline`, gli asset statici (`js/`, `css/`, `pwa/`) e gli script dei CDN del layout (stale-while-revalidate). **Mai** HTML dinamico (la stessa URL ha due risposte, pagina e fragment, distinte da `HX-Request`), non-GET, `/events` (SSE) e `/images/**` (Range/ETag, binari cifrati): passano sempre dalla rete. Nome della cache = ora e commit della build (`BuildInfo`): una release invalida la vecchia. Nome e nome breve del manifest da `app.title`/`app.brand` (per lingua); i colori sono esadecimali in configurazione (un manifest non accetta token Tailwind: unica eccezione alla regola del theming). Con il blocco con PIN attivo la shell resta raggiungibile perche' `hexa-pwa` implementa `ILockExemptPaths` (`/sw.js`, `/offline`, manifest, `/pwa/`). Serve HTTPS (`localhost` esente); offline reale solo dopo una visita online (i CDN si copiano a runtime). Non verificato dal vero: installazione in Chrome/Safari e prova offline nel browser.

## Filosofia e cosa NON introdurre

Hypermedia-first, non SPA: server → HTML. Spring MVC + Thymeleaf; aggiornamenti parziali htmx; micro-interattivita' Alpine; componenti complessi = Web Component isolato. Zero build frontend (htmx, Alpine, Tailwind da CDN in `fragments/core/layout.html`).

- **WebFlux come modello del server**: no (resta `spring-boot-starter-webmvc`). Eccezioni, solo tipi Reactor: il client HTTP di Spring AI e `EventStreamController` (`GET /events`, `Flux<ServerSentEvent<?>>` da `Sinks.Many` in `PushService`, porta `IClientPushStream`). La connessione SSE e' nel layout (`live-events :: connect`, su OGNI pagina: i toast devono arrivare ovunque) e la tiene UNA sola tab per browser (Web Locks `hexa-events`, ritrasmissione alle altre con `BroadcastChannel`; senza queste API ogni tab apre la sua): mai includerla di nuovo da una pagina (due connessioni per tab saturano le ~6 di HTTP/1.1).
- **React/Vue/Angular**: no. **Build step Tailwind obbligatorio**: no (opt-in `mvn -Ptailwind clean package`; config nel progetto dell'host (`src/main/tailwind/tailwind.config.js`, il cui `content` deve scansionare anche i template dei jar hexa-* estratti in `target/hexa-templates`); il blocco `@layer base` e' duplicato fra `input.css` e `layout.html`: tenerli allineati; classi sempre stringhe letterali).
- Nessun CSS in `static/`. Immagini in `./data/images`, DB di sviluppo in `./data/postgres` (fuori da git).

## Stack

Spring Boot 4.x + MVC; Thymeleaf + layout dialect; htmx/Alpine/Pines UI via CDN; Spring Data JPA + PostgreSQL/pgvector; Flyway (`ddl-auto: validate`); `RestClient` per i servizi remoti; Spring AI 2.0.x (OpenRouter, embedding ONNX locali, `PgVectorStore`); `commonmark` + `commonmark-ext-gfm-tables` 0.24 (versione esplicita nel pom); ArchUnit.

## Architettura (core/app, esagoni)

Ogni sottosistema e' un esagono in `org.dual.hexa.<modulo>.<s>`: `core`, `ai`, `pwa` e `oauth2` sono le librerie (generiche), `app` e' lo specifico. Solo `app → librerie`; `core` non conosce `ai`, `pwa`, `oauth2` ne' `app`; `ai`, `pwa` e `oauth2` dipendono solo dal core e non si conoscono (regole di `ArchitectureTest`). Fuori da questi solo `Application` e `support` (test).

```
<core|app>/<s>/ domain | application | port/in (I<Capability>) | port/out (I<Thing>Store|Gateway|...) | adapter/in/<tech> | adapter/out/<tech>
```

- **Naming**: interfacce SEMPRE con prefisso `I` (porte comprese), implementazioni senza, col ruolo/backend (`ISecrets` → `SecretService`). Repository Spring Data package-private in `adapter.out.persistence`.
- **Regole** (`ArchitectureTest` 14 regole + `SourceImportsTest`: una violazione si corregge nel codice, non allentando la regola): `domain` = JDK + `jakarta.persistence` + Hibernate types + kernel; `application` usa solo `port.out`/`port.in`, niente adapter/`org.springframework.web|http|ai|data|jdbc`/servlet/`java.sql`/IO file e immagini; `port` dipende solo da domain/port/kernel; `adapter.in` e `adapter.out` non si conoscono (eccezione `adapter.ai`); un controller parla solo con porte `in`. Fra sottosistemi si dipende SOLO da `port.in` e `domain`; nessun ciclo. `core.kernel`, `core.web`, `app.shared` sono condivisi e non dipendono da sottosistemi. **Nei commenti** citare classi di altri strati con `{@code Nome}`, mai `{@link}`.
- **Punti di estensione dell'app sul core** (elenco chiuso `ArchitectureTest.CORE_EXTENSION_POINTS`, valido anche per gli adapter delle librerie opzionali): `IEventLinkResolver`, `ISecretTypeCatalog` (piu' bean si SOMMANO); SPI pubbliche in `port.in` (`HOST_SPIS`): `IBlobReferences`, `ISearchableSource`, `IChatToolkit`, `IChatTurnContributor`, `IChatPageContributor`, `IChatOutcomeResolver`, `ICreditSource`. Le inietta il SERVIZIO (`Optional<...>`).
- **Grafo**: in hexa-ai `llm` e `search` sono foglie; `chat` → `llm`, `search`, `core.manual`; `credits` foglia. `ai.search` non conosce le entita' dell'host (legge i dati via `ISearchableSource`). `/deep-chat` e `/search` sono nel core con slot dell'host.
- **Autoconfigurazione**: `HexaCoreAutoConfiguration`/`HexaAiAutoConfiguration`/`HexaPwaAutoConfiguration`/`HexaOauth2AutoConfiguration` (`META-INF/spring/...AutoConfiguration.imports`) scansionano i propri sottosistemi e (core, ai, oauth2) li registrano come package JPA (`SubsystemPackagesRegistrar`): un host con qualunque package radice non scrive scan ne' `@EntityScan`. I package vi sono spezzati (`"org.dual.hexa" + ".core."`, `".ai."`, `".pwa."`, `".oauth2."`) per non farli leggere a `SourceImportsTest`. Flyway: nessuna location, il default `classpath:db/migration` scansiona le sottocartelle.
- **Nuovo sottosistema/feature**: core o app? Disegnare PRIMA le porte (tipi di dominio o `core.kernel.Paged`, mai web/HTTP/Spring Data/Spring AI), poi gli adapter; se serve un dato di un altro sottosistema senza che ti conosca, definire una SPI nella tua `port.in`.
- **Variabili d'ambiente**: quelle che configurano i moduli hexa-* (core e ai) hanno il prefisso `HX_` (`HX_DB_*`, `HX_STORAGE_TYPE`, `HX_STORAGE_WEBDAV_*`, `HX_BACKUP_ENCRYPTION_KEY`, `HX_OPENROUTER_*`, `HX_SEARXNG_USERNAME|PASSWORD`, `HX_LOCK_RESET`, `HX_OAUTH2_*`) e vanno lette con un placeholder esplicito in `core.yml`/`ai.yml` (o `@Value` annidato per le chiavi con default nel codice); quelle dell'app/host restano senza prefisso (`REPLICATE_API_TOKEN`, `SEARXNG_BASE_URL`). Una nuova variabile di un modulo hexa-* nasce con `HX_`.
- **Config**: `application.yml` (solo app) importa `core.yml`, `ai.yml`, `prompts.properties`; chiavi disgiunte. **Un file IMPORTATO vince sull'`application.yml` che lo importa** (solo i profili `application-<profilo>.yml` vincono): una chiave di `core.yml`/`ai.yml` non si cambia dall'host; per questo in `ai.yml` stanno solo default stabili. Bundle `messages-core(.en)` + `messages-ai(.en)` + `messages(.en)` (`messages-ai` aggiunto da `AiMessagesConfig`). `core.yml` NON ha default per `HX_DB_NAME`/`HX_DB_USERNAME` (sono dell'app, nel `.env`). `app.layout.nav=top|sidebar` (`SidebarLayoutTests`). Punti di estensione del layout: `fragments/app/nav.html :: links`, `status-extras.html :: container`.
- **Barra in basso/crediti** (`ICredits`): il render NON fa chiamate remote, il chip carica `GET /credits/bar` via htmx. OpenRouter richiede una MANAGEMENT key (`HX_OPENROUTER_MANAGEMENT_KEY`, senza il chip non compare). Le altre fonti di credito dell'host si innestano con la SPI `ICreditSource`.

## Pattern Thymeleaf e controller

- **Due subtree di fragment, `app → core`** (`TemplateLayeringTest`): `fragments/core` = generico (kit UI, layout, feature infrastrutturali), conosce l'app solo via `fragments/app/nav` e `status-extras`; `fragments/app` = solo dominio. I fragment generici ricevono testi e URL gia' risolti come parametri (mai `#{app...}` ne' bean dell'app); i wrapper sottili dell'app li risolvono. In un parametro di fragment NON si usano `@bean`, `new`, `T(...)` ne' mappe SpEL: calcolarli con `th:with`.
- Ogni pagina: `layout:decorate="~{fragments/core/layout}"` sul proprio `<html>` (senza `lang` letterale) e contenuto in `<div layout:fragment="content">` (NON un `<main>`). `<title>` sostituisce quello del layout. Pagine in `templates/{app,core}/`.
- **Stessa URL, due risposte** distinte da `HX-Request` (fragment/pagina intera). Un fragment con parametri restituito come vista diretta richiede parametri **nominati**; la forma posizionale vale solo in `th:replace`.
- **Breadcrumbs** su OGNI pagina tranne la Home: `fragments/core/breadcrumbs :: trail(group, parentPath, parentText, current)` nello slot `breadcrumbs`, parametri nominati e tutti passati (inutilizzati `null`), `parentPath` grezzo (`everyPageButHomeShowsBreadcrumbs`).
- **Menu**: `header.menu.manage` in `messages-core`, `header.menu.create` nell'host.

## Convenzioni

- **URL dell'app**: ogni attributo con un URL (`href`, `src`, `action`, `hx-*`, `connect`) passa SEMPRE da `@{...}` (reverse proxy su subpath, `X-Forwarded-Prefix`): `th:hx-post="@{/x}"`; fuori da htmx `th:attr` con `@{...}` in `|...|`. Lato Java `request.getContextPath() + "/gallery"`; `redirect:` no.
- **Theming**: solo Tailwind, utility inline; mai colori hardcoded fuori da `theme.extend.colors`; token `{ DEFAULT, dark }` (`canvas|surface|ink|ink-muted|line|accent|accent-contrast|danger|favourite|warning`) come `bg-canvas dark:bg-canvas-dark`. Dark mode `['selector', '[data-theme="dark"]']`; lo script di boot in `<head>` non si sposta (FOUC). `@layer base` solo per elementi "nudi"; mai nuove regole `@layer`.
- **Bottoni**: mai `<button>` a mano; fragment di `fragments/core/button.html`, `core/field-buttons.html` (o un fragment dell'host: aggiungerne uno se nessuno calza), parametri nominati e TUTTI passati.
- **Alpine**: i binding non passano da `th:attr`/`#{...}`: valore dinamico in un `data-*` e `$el.dataset`.
- **Componenti Pines**: l'elenco di quelli supportati (select, accordion, popover, video, lightbox, paginazione, modal, full-screen modal, tabs, switch, slideover, dropdown, copy to clipboard) e' in `manual/it/02-architettura/03-web-htmx-thymeleaf.md` ("Componenti Pines supportati"): un nuovo componente = fragment in `fragments/core`: dialog = `modal :: dialog(titleId, maxWidth, body=~{::#id})`, schede = `tabs :: list/tab`, booleani di form = `switch :: toggle` (mai checkbox nude), pannello ancorato con bottone proprio = `popover :: floating`, pannello laterale di navigazione = `slideover :: drawer`, copia negli appunti = `copy-to-clipboard :: copy`; conferma di un'azione = `hx-confirm` (o `window.hexaConfirm(domanda)` da JS: Promise<boolean>), reso da `confirm-dialog`, mai `confirm()` nativo (`ConfirmDialogTest`); mai scheletri scritti a mano; script in `layout.html`, riga in quella tabella.
- **Campi svuotabili**: ogni `<input>` testo/search/date/number si avvolge con `fragments/core/clear-field :: wrap(content=~{::#id}, clearable=..., title=...)` (id univoco; `clearable=false` = nudo; mai un reset a mano). Scrittura da codice del valore = `clear-field:sync` sull'input. Opt-out gia' fatti: pill di `tag-chips`, `confirmText`, `version`, readonly.
- **Select**: mai `<select>` nuda; wrapper `pinesSelect` (`fragments/core/select.html`), la `<select>` nativa resta fonte di verita'; un cambio da codice si annuncia con `select.dispatchEvent(new Event('pines-select:sync'))` (`everySelectIsWrappedByThePinesSelectComponent`).
- **i18n**: ogni testo utente-visibile da `MessageSource` + `#{...}`; lingua da `Accept-Language`, default italiano. Bundle `messages-core*`/`messages-ai*`/`messages*` con chiavi **DISGIUNTE** (una chiave nuova nel bundle del lato del codice che la usa, in ENTRAMBE le lingue). Chiavi `<pagina-o-componente>.<categoria>.<elemento>`. Il testo del core NON nomina servizi dell'app. **Apostrofi** raddoppiati (`''`) nei messaggi con argomenti; argomenti numerici `{0,number,#}`. Java: errori all'utente con `core.kernel.i18n.Messages`, risolti al call site prima dell'eccezione.

### Errori, eventi di sistema, remoti
- Ogni chiamata a OpenRouter/SearXNG o altro servizio remoto e ogni errore interno passa da `ISystemEvents#record(operation, throwable[, subject])`: MAI un `catch` che ingoia o solo logga. `record` non lancia e consegna il toast alla prima occorrenza di una serie (5 min). Avvisi: `warn(source, operation, subject, message)` (messaggio gia' tradotto). Registra chi gestisce/ingoia l'eccezione (servizi in background, tool, watcher); se risale a un controller, il controller.
- **Toast**: header `HX-Trigger` via `HtmxEvents#addToastHeader`/`addHxTrigger`. Nessun bottone "Riprova" sul toast (rieseguire una POST creerebbe una seconda prediction a pagamento).
- **Notifiche** (`core.events`, di pertinenza del core): tre strade, un solo contenitore (`fragments/core/toast.html`, evento `system-toast`). Errori e avvisi = `ISystemEvents` (registro, campanella, SSE `system-event`, header `HX-Trigger`). **Successi effimeri** (cio' che finisce in background: un lavoro riuscito) = `INotifications#success(key, messageGiaTradotto, path)`: SSE `notice`, NIENTE registro ne' campanella (un successo non passa da `ISystemEvents`, e `notice` non e' `system-event`: quello aggiorna anche `/system/events`). `key` = dedupe lato client; `path` = link «Apri» (senza context path). Il testo e' risolto all'emissione (dal watcher in background vale la lingua di default). Un host emette un successo cosi', mai con un suo evento SSE + toast a mano.
- **Overlay "operazione in corso"** blocca la UI durante i non-GET htmx; `data-busy="off|on"`, `data-busy-text`, `data-busy-delay`; watchdog `htmx.config.timeout` 180 s; fuori scope i turni di `/deep-chat`.
- **Chat**: se l'LLM fallisce `SpringAiAssistant` lancia `AssistantException` e `ChatService#reply` scrive un turno ASSISTANT d'errore (`ChatMessage.error`, mai rimandato all'LLM) e lancia `DeepChatFailedException` (gia' registrata).
- **HTTP**: `spring.http.clients.*` vale per tutti i `RestClient.Builder` auto-configurati; un nuovo client usa il builder iniettato, mai `RestClient.create()`.
- **`core.kernel.remote`**: `RemoteServiceException` (radice delle eccezioni dei servizi) porta `source()` e `kind()`: `TRANSIENT`, `PERMANENT`, `CONFIGURATION`, `REJECTED` (atteso, non si registra). Il resolver risponde 502 / 422 (toast, niente evento) / 500. `RemoteCaller#call` ritenta solo i `TRANSIENT`; **`RetryPolicy.NONE` ESPLICITA per le operazioni NON idempotenti/a pagamento** (es. la creazione di una risorsa a pagamento). `RestClientTranslator` = unica regola stato HTTP → `Kind`. Un'eccezione di servizio costruita con il solo messaggio = `REJECTED`: un errore vero senza causa va costruito con `Kind` esplicito. **Nuovo servizio remoto**: valore in `*EventSource` + `events.source.<X>` nelle due lingue; `FooException extends RemoteServiceException`; client `extends RestRemoteClient` che implementa la `port.out`, ogni chiamata in `remote.call(...)`.

## Storage dei binari

Tutto cio' che l'app serve come file passa da `IImageStorageService` (nessun accesso diretto a filesystem/WebDAV, nessun resource handler statico: `/images/**` e' di `ImageController`, Range + ETag). Backend `storage.type=local|webdav`. Lancia SOLO `StorageException`. La porta espone `UploadedFile`, non `MultipartFile`.
- **Nomi**: ogni binario nuovo = `StorageNames#newFilename` (`<sha256 di 32 byte casuali>.<ext>`), mai derivato da id/URL/nome originale, nessuna dedup. Layout `ab/cd/<filename>` (`shardPath`); i vecchi file piatti non sono piu' serviti.
- **WebDAV**: contenuti SEMPRE cifrati AES-256-GCM a chunk (`ChunkedAesGcmCipher`) con `storage.webdav.encryption-key` (base64 di 32 byte, mai nel repo; persa = binari irrecuperabili). PUT su `.part` + MOVE; le scritture ritentano i soli transitori, le letture per `/images/**` NO. Cache `EncryptedBlobCache` (blob CIFRATI).
- **Migrazione locale → WebDAV** (`LocalToWebDavMigrator`): una tantum, `storage.migration.from-local.enabled=true`, riavviabile; a fine giro rimettere `enabled=false`.

## Migrazioni (Flyway)

Ogni modifica alla persistenza = **nuova migrazione SQL PostgreSQL** in `db/migration/{core,ai,oauth2,app}`, nome `V<AAAA>_<MM>_<GG>_<HHMM>__<descrizione>.sql`, SEMPRE successiva a tutte le esistenti di tutte le location (`outOfOrder=false`); mai modificare un file eseguito (il checksum fa fallire l'avvio). **Nessuna FK dal core all'app**; le colonne di collegamento fra feature sono `Long` (mai `@ManyToOne` verso un altro esagono); la FK c'e' solo nella direzione delle dipendenze. Le baseline vincolano l'ordine: core `1200`, ai `1210` (tabelle `chat_*`, `vector_store`, `CREATE EXTENSION vector`), app `1220` (re-baseline 2026-10-07: i DB precedenti vanno ricreati). `generation.conversation_id` NON ha FK. Dialetto: identificatori minuscoli non quotati, testo lungo `text` + `@JdbcTypeCode(SqlTypes.LONGVARCHAR)` (MAI `@Lob`), `timestamptz`, `bytea`, enum Java = `varchar` senza ENUM/CHECK. Un modello nuovo = `INSERT` in `replicate_model`. In sviluppo: `docker compose down && rm -rf data/postgres`.

## Segreti

UN'unica entita' `Secret` (`core.secrets`, tabella `secret`) con un **tipo** stringa, CRUD in `/secrets` (`GET /tokens` rimanda li' con un redirect permanente). Il core registra `API_TOKEN`, `PASSWORD`, `GENERIC`; l'host e i moduli aggiungono tipi con `ISecretTypeCatalog` (PIU' bean si sommano, l'etichetta e' `secrets.type.<NOME>` nel bundle di chi lo registra, gli identificatori sono MAIUSCOLI). Un tipo `managed` e' di un modulo: elencato in `/secrets` ma non creabile, modificabile ne' cancellabile da li' (`ISecrets#store`/`deleteByNamePrefix` per il modulo proprietario). Le form filtrano per tipo (`ISecrets#options(type)`). Dopo il salvataggio solo gli ultimi 4 caratteri; mai il valore in log, eventi, toast o Model. Cifratura `ISecretCipher` con la STESSA chiave dei binari WebDAV (`app.secrets.encryption-key`); con `storage.type=local` senza chiave `isConfigured()` e' falso e salvare e' `CONFIGURATION`. Chiave persa = segreti irrecuperabili. Un segreto scaduto o inesistente al momento dell'uso = `REJECTED`: l'operazione non parte.

## Ricerca semantica (`ai.search`; pagina `/search` = `app.search`)

Stesso Postgres. Spring AI (`Document`/`Filter`/`VectorStore`) non esce dall'adapter `adapter.out.vector` (`IVectorIndex` → `PgVectorIndex`).
- **Embedding** `multilingual-e5-small` quantizzato (384 dim, ~120 MB in `./data/models`); i prefissi `passage: `/`query: ` li applica `E5PrefixEmbeddingModel`. Punteggi compressi (0.7-0.9): top-K, non soglie fisse. `vector_store` da Flyway (`initializeSchema=false`), **nessun indice ANN** di proposito (un indice approssimato tronca a `ef_search`). Filtro `DocumentFilter` → jsonpath: EQ, NE, IN, NIN, AND, OR, GT/GTE/LT/LTE (NON NOT/ISNULL).
- UN documento per ogni entita' indicizzata dell'host (via `ISearchableSource`); testo = contenuto + (dopo `TAGS_SEPARATOR`) tag d'indice (UI e `ArchiveSearchTool` mostrano `visibleText`). Metadata `type`, `refId`, ecc.; chiavi **riservate** di `VectorIndexer`: `contentHash`, `embeddingModel`, `indexedAt`.
- `ArchiveIndexService`: riconciliazione idempotente su tutti i bean `ISearchableSource`, in background e dopo gli eventi dell'host (`@TransactionalEventListener(fallbackExecution = true)`); rimuove i documenti dei `types()` la cui riga non esiste piu'. Una nuova fonte = un nuovo `ISearchableSource` nel suo sottosistema.
- `app.search.enabled=false` (test) spegne indice, scheduler, tool ed `EmbeddingModel` (usa `FakeEmbeddingModel`). Prove reali: `mvn test -pl hexa-ai -Dtest=E5ModelSmokeTest -Dsemantic.model.test=true`.
- UI: UN form e UNA lista paginata (`GET /search/results`); testo = classifica sopra soglia (default 80%), senza testo = piu' recenti. Solo le note (`type=note`) sono modificabili (`IArchiveNotes`), i derivati in sola lettura. Slot dell'host in `app.search.host-fragment`. Nei test i documenti derivati finti possono essere cancellati dalla riconciliazione: per liste lunghe usare `type=note`.

## Backup e restore

`java -jar app.jar export <file> [--no-encrypt]` / `import <file> [--replace]` (esito 0/1/2). Esagono `core.backup` generico; parte da `Application.main` col profilo `backup` (`WebApplicationType.NONE`, un `ApplicationRunner` esegue ed ESCE, i listener "all'avvio" non partono); il profilo spegne recovery, search, token check, migrazione, cache. Tutti i bean tranne `IBlobReferences` sono `@Profile("backup")` (`BackupProfileContextTest`).
- **Formato**: zip in streaming (`manifest.json`, `blobs/`, `db/<tabella>.copy`, `summary.json`; DEFLATED sempre), cifrato = l'INTERO zip in formato `DFX1`. DB via `COPY` con `CopyManager` (non `pg_dump`), TUTTE le tabelle tranne `flyway_schema_history`, `vector_store` compresa (**le note manuali vivono SOLO li**); export in UNA transazione REPEATABLE READ; ordine topologico sulle FK (`TableOrder`).
- **Binari**: quelli REFERENZIATI dal DB (SPI `IBlobReferences`; `BackupBlobColumnsTest` fa fallire una colonna `%filename%` non dichiarata). Letti/scritti da `IImageStorageService`.
- **Import**: controlli in sola lettura → **binari prima** → **DB per ultimo**, in transazione (Flyway `migrate` fino alla versione del backup, `TRUNCATE ... RESTART IDENTITY CASCADE`, `COPY`, `setval` di OGNI identity, verifica righe) → `migrate` all'ultima. Un backup vecchio entra in un jar nuovo, non viceversa. Se il caricamento fallisce il DB resta migrato ma vuoto: rilanciare con `--replace`.
- **Credenziali**: solo `HX_DB_*` e, con WebDAV, `HX_STORAGE_WEBDAV_*`; mai `REPLICATE_*`, `HX_OPENROUTER_*`, `HX_SEARXNG_*`. `backup.encryption-key` = `${HX_BACKUP_ENCRYPTION_KEY:${storage.webdav.encryption-key:}}`: export senza chiave RIFIUTA (serve `--no-encrypt`); la chiave NON e' nel backup. `secret.value_encrypted` si copia com'e': con un'altra chiave non si apre (avviso a fine import).

## Manuale online (`core.manual`)

Markdown in `src/main/resources/manual/<lingua>/<NN-gruppo>/<NN-pagina>.md` (Uso per l'utente, Architettura per chi sviluppa), servito da `/manual`; il bot lo consulta con `ManualTool` (solo gruppo `uso`). **Slug = nome file senza prefisso, unico fra tutti i gruppi**; etichetta del gruppo `manual.group.<gruppo>` nel bundle dell'host; titolo = primo `# `; una lingua senza cartella ricade su `it`; contenuto con gli accenti veri.
- Una **sezione** (da `#`/`##` al successivo) e' l'unita' cercata e citata; **ancore** da UNA sola `HeadingSlugs` (i titoli non possono avere formattazione inline). Link nei `.md`: fra pagine il nome VERO del file (`../01-uso/03-x.md#ancora`), verso l'app un path radice dell'host (`/settings`), `#ancora`, `http(s)://`.
- `CommonmarkRenderer` con `escapeHtml(true)` e `sanitizeUrls(true)`; `manual.html` usa `th:utext` solo sui due `<div>` dell'articolo; niente `@layer`/Typography (varianti arbitrarie Tailwind definite UNA volta con `th:with="prose=..."`). Test: `ManualContentTest` (slug unici, un solo `#`, sezioni <= 6.000 car., link e ancore esistenti), `ManualControllerTest`. Con Maven 3.8.1 su JDK 24 il TLS del mirror puo' fallire: `-Dhttps.protocols=TLSv1.2,TLSv1.3`.

## Comandi e test

```bash
mvn -q install -DskipTests          # installa le librerie nel repository locale
mvn test                            # test di tutti i moduli (richiede Docker)
mvn test -pl hexa-integration-tests -am -Dtest=ArchitectureTest -Dsurefire.failIfNoSpecifiedTests=false   # solo architettura (senza Docker)
```

`mvn test` non tocca mai il DB di sviluppo: `PostgresTestContainerInitializer` avvia UN container `pgvector/pgvector:pg17` e Flyway applica lo schema reale. Surefire fissa `storage.type=local`, la migrazione spenta e una chiave di test (battono il `.env`); un test WebDAV li sovrascrive con `@SpringBootTest(properties=...)`, mai contro il server vero. I test condividono il DB: i `@SpringBootTest` che scrivono ripuliscono a mano o sono `@Transactional`. **Mai chiamate vere a servizi remoti (OpenRouter...) nei test**: `@MockitoBean` per le porte `out` verso l'esterno; `MockRestServiceServer` per i client; con uno stub gia' lanciante ri-stubbare con `doReturn(...).when(mock)`.

## Checklist per una nuova pagina/feature

1. Navigazione → controller in `adapter/in/web` (solo porte `in`) + template col layout manager; voce in `nav.html` e breadcrumbs.
2. Aggiornamento parziale → fragment in `fragments/app/` (o `core/`), restituito se `HX-Request`.
3. Interattivita' locale → Alpine; componente complesso stateful → prima un Web Component isolato.
4. Tocca un'entity → migrazione Flyway nella location giusta; nessuna FK core → app.
5. Testo visibile → chiave nel bundle giusto in entrambe le lingue.
6. `<button>` → fragment; `<select>` → `pinesSelect`.
7. Evento che l'utente deve notare → `ISystemEvents#warn`/`#record`.
8. Nuovo sottosistema/porta/dipendenza → `ArchitectureTest` verde.
9. Cambia cio' che l'utente vede o fa → aggiornare il manuale (`manual/it/01-uso/`, o `02-architettura/`): `ManualContentTest` blocca solo i link morti, non il testo vecchio. Etichette come nei bundle con gli accenti veri; per icone e pulsanti il titolo che l'utente vede (si controlla nel template).
